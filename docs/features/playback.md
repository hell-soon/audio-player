# Воспроизведение и устройства

Подробности к `AGENTS.md` (общие правила проекта — там). Качество, кроссфейд, кэш треков в SW, быстрое листание, Spotify «Device not found», подключение устройств, «продолжить с того же места», скорость.

- **Качество звука** (`player.quality`: auto | lq | nq | hq, параметр `?quality=` у `/api/yandex/stream` и `match-stream`): «Авто» — hq, в мобильной сети nq, при Save-Data lq. Если `get-file-info` не принял качество — запасной `download-info` выбирает битрейт сам.
- **Умный кроссфейд** (`smartCrossfade`): треки одного альбома подряд не накладываются; наложение ≤ ¼ более короткого трека.
- **Кэш следующих треков** (`prefetchUpcoming` → `postMessage('prefetch-audio')` → `public/sw.js`): SW скачивает 3 следующих трека в `audio-*` (до 5 шт.) и отдаёт их `<audio>` с поддержкой Range (206 — иначе Safari не играет). Работает, только если CDN Яндекса отдаёт CORS, иначе тихо выключается. SW вмешивается в `/api/yandex/stream*` только при попадании в кэш или без сети.
- **Подключение устройств** (`model/connect.ts`, решение — `docs/adr/0001`): каждое окно сайта — устройство. Онлайн-устройства держат друг с другом **прямой канал WebRTC** (`lib/device-link.ts`, STUN Google, без TURN): по нему команды (`{t:'cmd'}`) и состояние (`{t:'hello'}` — при изменении и раз в 5 с, это же «жив»; 20 с тишины — канал мёртв). Договариваются через сервер: команда `signal` с SDP **без trickle** (ждём сбора ICE ≤ 2 с — один offer и один answer через опрос); начинает устройство с меньшим id. Нет канала — команды через `/api/devices/command`, как раньше. Опрос `/api/devices/sync` (на Vercel нет WebSocket): 1 с, пока договариваемся; 15 с, если со всеми есть канал; иначе 1,5 с при взаимодействии, 4 с в простое; скрытая вкладка без музыки не опрашивает вовсе (бережём лимиты Neon), но по живому каналу видна и принимает перенос. «В сети» на сервере — 40 с. Вкладки одного браузера — одно устройство (общий `device:id` в localStorage).
- **Одно активное устройство:** когда звук пошёл (`watch(isPlaying)` → `connect.playingChanged`), устройство рассылает по каналу `claim` со временем старта; играющее устройство с более ранним стартом затихает (`fadeOutPause(800)`) и становится пультом. После настоящей паузы (≥ 3 с, не смена трека) — ещё `pause` через сервер устройствам без канала и, если подключён Spotify, пауза колонке/приложению Spotify (`/api/spotify/connect/state`, не чаще раза в 30 с; свой браузерный плеер — `spotifyDeviceId()` — не трогаем).
- **Перенос без паузы:** `play-queue` с `transfer: <id источника>`; источник **не** ставит паузу, а ждёт `claim` от цели (5 с по каналу, 15 с без него) и затихает за 0,8 с. Цель не смогла начать (автозапуск — `onError(…, autoplayBlocked)`) → шлёт `blocked`: источник играет дальше и пишет «нажмите там „Играть“». Нет ответа — «Не удалось перенести». «Играть» во время затухания отменяет его. На Spotify Connect — как раньше: сразу пауза здесь.
- **«Продолжить с того же места»:** при синхронизации устройство отправляет снимок очереди (только при изменении) в `devices.queue`; при открытии сайта `initPlayer` берёт `/api/devices/resume` и через `restore()` показывает последний трек на паузе с той же позиции (`pendingStartMs`). Если что-то играет на другом онлайн-устройстве — вместо этого плеер становится пультом. Устройства Spotify Connect — с префиксом `sp:` (через `/api/spotify/connect/*`). Если `controlling` не null — `usePlayer()` показывает состояние удалённого устройства, а действия уходят ему командами; UI об этом не знает.
- **Скорость треков:** функции Vercel — `fra1` (`nitro.vercel.functions.regions`, рядом Neon); аккаунты кэшируются в памяти 60 с (`getAccount`, сброс `forgetAccount` при любом изменении); ссылка на поток — 90 с (`u:ID:stream:…`), заголовок `Server-Timing` у `/api/yandex/stream`. Клиент: следующий трек предзагружается через 4 с после старта (в мобильной сети — за 30 с до конца), касание строки трека «разогревает» ссылку (`player.warmTrack`).
- `findYandexMatch` пробует запасные запросы (только название; название + остальные исполнители), если «исполнитель + название» не нашёл. 403/404 текста от Яндекса — норма (нет прав на текст), не логируется, берётся LRCLIB.
- **Быстрое листание треков**: ошибка `<audio>` с `MEDIA_ERR_ABORTED` — не ошибка трека (прерванная загрузка прежнего); перед «трек недоступен» — один повтор того же `src` (`retried`). Заказ «скачать следующие» (`prefetchUpcoming`) — только если через 4 с играет всё тот же трек. Асинхронные цвета обложки (`AmbientBackdrop` — оттенок, `LivingBackground` — палитра, `useCoverAccent`) применяют только ответ последнего запроса (счётчик `seq`), иначе цвет пролистанной песни приходил позже и перекрашивал фон.
- **Spotify «Device not found» (404 на `/me/player/play`)**: Spotify забывает браузерный плеер после сна компьютера, долгой фоновой вкладки, обрыва SDK. Сервер после своего повтора отвечает понятной 404 (`data.code: 'device-gone'`), клиент (`spotifyPlay`) переподключает SDK (`disconnect` → `connect`, ждёт новый `device_id` до 8 с) и повторяет; не вышло — ошибка `code: 'device-gone'`, и `startCurrent` играет этот трек через Яндекс (следующий снова пробует Spotify). **Держим плеер подключённым** (`spotify-engine.ts`): `not_ready` → переподключение с повторами (1/5/20 с); возврат на вкладку после ≥ 60 с, событие `online` и пробуждение компьютера (разрыв таймера > 90 с) → `GET /api/spotify/device-alive?id=` (видит ли Spotify наш device_id), нет — переподключаем заранее. Опрос в фоне не делаем — лимиты API Spotify.
