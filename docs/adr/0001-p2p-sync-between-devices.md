# Синхронизация воспроизведения — напрямую между устройствами (WebRTC), сервер только для договорённости и запаса

Команда с пульта должна доходить быстрее 0,5 с, а перенос воспроизведения — давать не больше 1 с тишины. При этом никаких внешних сервисов: только Vercel (нет WebSocket) и Neon по HTTP (`neon-http`, сервер не может «толкнуть» устройство). Поэтому команды и состояние идут по прямому каналу WebRTC (DataChannel) между всеми онлайн-устройствами пользователя, вкладки одного браузера — через `BroadcastChannel`. Сервер (`/api/devices/sync`) лишь передаёт сигналы для установки соединения, хранит снимок для «продолжить с того же места» и остаётся запасной доставкой, если прямого канала нет; пока канал жив, опрос — раз в 15 с.

## Considered Options

- **Внешний realtime (Ably, Pusher, Upstash)** — отвергнут: не хотим зависеть от стороннего сервиса.
- **SSE / долгий запрос на Vercel с опросом Neon каждые ~200 мс** — отвергнут: Neon не засыпает, функции висят постоянно, бесплатные лимиты кончаются.
- **Чаще опрашивать (0,5 с)** — отвергнут: до цели не дотягивает и съедает лимиты.

## Consequences

- Нужен публичный STUN (Google, без аккаунта); TURN нет — в строгих сетях (симметричный NAT) прямой канал не встанет, и устройство работает по опросу с прежними задержками.
- Скрытая вкладка без музыки остаётся целью переноса, пока жив её прямой канал, хотя на сервер она не ходит.
- Порог «в сети» — 40 с (опрос реже), поэтому серверный список устройств устаревает дольше; свежесть онлайна берётся из прямого канала.
